## Headline

**11 of the 12 favourited templates resolve against the live Platform API.** One
(`Mixam MXM-COMIC`) has no live template with that name. This card's acceptance criterion of
"12 resolved" is not met and cannot be met — not because the templates are unavailable, but
because that one does not exist in this shop's catalogue under any name.

Two earlier readings of this API said otherwise and both were wrong:

- **"only 1 of 12 exists"** (previous run of this card) — false. `GET /product-templates`
  returns **25 rows while `total` says 605**, and `?page=` / `?size=` are silently ignored:
  every page returns page 1's ids. Reading the list endpoint's length as the catalogue size
  undercounts by 24×. → **T34**
- **"605 templates, 274 backend-renderable"** — **correct**, confirmed live. 605 ids seeded from
  the integrated catalog CSV, 605 resolved, 0 absent, 0 transient.

So the earlier scope decision ("re-scope to apparel + drinkware; mugs, wall art, candles,
coasters and rug all drop out") rested on a false premise. **Those categories are all present
and buildable.**

## Sizes — recorded as `none-exposed-by-api`

**No template in the 605-template catalogue exposes a `sizes` or `sizeVariants` array.** The
detail document's complete key set is:

```
brand, category, colorVariants, customizableAreas, description, minimumOrdersNumber,
name, priceFrom, priceTo, productId, productionMethod, sizeGuide, slug,
supportsBackendRendering
```

The only size-adjacent fields are `sizeGuide` (measured `{url: null, content: null}` on all
four templates spot-checked) and the `minimumOrdersNumber` scalar. A template's accepted sizes
**cannot be read from this API at all**, so the artifact records
`"sizes": "none-exposed-by-api"` rather than inventing values.

This is a live risk for **T06** and worth being blunt about: omitting `sizes` from a create
payload produces exactly one variant, and that bug is on four mugs in production now. If sizes
cannot be enumerated from the template API they must come from the dashboard per template, or
the products get created with one variant each. **This needs a decision before `t_5a646577`
authors any config** — it is not solvable by further probing.

> An earlier revision of this note listed concrete size arrays per template (`["Slim 12 oz",
> "Regular 12 oz"]`, 46 canvas sizes, 14 poster sizes, …). Those came from the **MCP browse
> catalogue**, not the Platform API, and the Platform API does not expose them. They may well be
> correct — but they are unverified against the surface the seeder writes to, so they have been
> removed rather than presented as measurements.

## `available` is not a usable signal

**31 of 605 templates have every area reporting `available: false`** while being live and
orderable — including the Coozie, both of whose areas report `false`. The old
`getTemplateAreas()` filter (`a.available !== false`) returned an **empty array** for those,
which reads as "no printable region" and would have silently stopped the release. The filter is
removed; areas are returned as-is and the caller decides. Recorded in the docstring so it is not
"tidied" back.

Conversely all 9 buildable favourited templates report `available: true`, so filtering on the
flag would not have lost them — it would only have produced false negatives on the others.

## Blockers for the downstream cards

1. **The 14-template margin table is void.** It was built on "the API exposes 25 templates, 14
   buildable". The real numbers are 605 and 274. Any pricing decision needs re-deriving against
   the corrected catalogue.
2. **Sizes cannot be read from the API** (above). This gates `t_5a646577` and is a **T06
   correctness risk**, not merely a data gap.
3. **4 of the 12 are not backend-renderable.** If the release stays scoped to the favourited 12
   it is 7 products, not 12. Re-scoping to the catalogue offers 274 candidates — but that is a
   new product decision, not a correction.

   this needs no new decision — but the reason is now "no such template in this shop's
